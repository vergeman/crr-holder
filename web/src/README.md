# Data access

The request flow is:

`React components → TanStack Query hooks → provider → WASM worker or HTTP client`

- `data/hooks.js` contains the handwritten TanStack Query hooks. They manage
  query keys, caching, and loading/error states through the selected provider.
- `data/provider.js` selects the data-access implementation. It calls the
  selected WASM worker or generated HTTP client for all five query methods.
  Both implementations return the same response shapes.
- `generated/client.ts` contains HTTP functions and types generated by Orval
  from FastAPI's OpenAPI schema. Do not edit it by hand. The development script
  regenerates it at startup and when the schema changes.

Keep components and hooks independent of the HTTP client. Handwritten code stays
outside `generated/` so regeneration cannot overwrite it.

## Browser SQLite providers

Use the header's **Data provider** selector to switch between **WASM full
download**, **SQL HTTP VFS**, and **HTTP API**. Changing it reloads the page,
resets portfolio filters, and starts a fresh provider session.

Open `/` for WASM execution of all five query methods. Each method can be
switched independently with `?metadata=http`, `?summary=http`, `?sources=http`,
`?sinks=http`, or `?contracts=http`.
Use `?provider=http` to select HTTP for all five, or `?provider=vfs` to select
the HTTP VFS for all five. Per-method parameters override `provider`; for
example, `?provider=vfs&metadata=http` keeps metadata on the API.
The default remains the full-download WASM provider.

Nonempty account filters select complete direct-account SQL variants in both
Python and the worker, preserving account-index use without SQL text expansion.

The worker assembles the same responses as Python: dropdown choices, portfolio
metrics, complete geography, top-100 rankings, and source holdings with 20-row
pages, zero-filled timelines, bounds, and next-page offsets. Sink expansion
preserves ranked rows and monthly cells. Contract details preserve holder and
time-of-use grouping, segment order, and totals. The contract grand total uses
compensated summation to match Python 3.12's `sum()`.

The first WASM request downloads the existing SQLite file from `/api/database`
through Vite's API proxy, then transfers its buffer to
`data/sqlite.worker.js`. The worker loads the shared statements from
`/api/source-sql/{statement}`, `/api/metadata-sql/{statement}`, and
`/api/summary-sql/{statement}`. The API serves the
file directly; no database copy or new stored representation is created.
SQLite WASM imports it read-only in memory. There is no OPFS or persistent cache.

Each browser provider in `data/wasmProvider.js` shares one worker and database
across its five methods, filters, and pages until page reload. Mixed provider
selections can create both workers.
A canceled request stops awaiting its response; the shared download and any
synchronous SQLite execution continue. Reload to get an updated dataset.

The page console logs download size and time. The worker console logs SQLite
version, import/setup time, and query/assembly time tagged by method.

The current database is 398,688,256 bytes (about 380 MiB). Initial loading needs
that entire transfer plus memory for the downloaded bytes and WASM database;
this experiment measures the full-download approach, without a range-reading VFS.

Runtime: pinned `@sqlite.org/sqlite-wasm` 3.53.4-build2, using its OO API and
`sqlite3_deserialize` in a dedicated worker. The standard memory backend does
not need OPFS or cross-origin isolation headers. WASM assets are bundled by Vite;
the API serves the SQL assets and dataset in both development and built clients.

## HTTP VFS experiment

Open `/?provider=vfs` to read the existing database on demand through HTTP
ranges. The API's `/api/database` endpoint supports HEAD for file-size discovery
and GET with Range for partial reads (206 with Content-Range). Unsatisfiable
ranges return 416. The same endpoint still supports the full-download provider.
Requests stay on the existing same-origin Vite API proxy.

The VFS provider uses pinned `sqlite-wasm-http` 1.2.0, which bundles SQLite
3.44.2. It uses the library's synchronous HTTP backend inside the dedicated
worker, with its default in-memory cache. The full-download provider keeps
SQLite 3.53.4. Both execute the same SQL and JavaScript response assembly.
No SharedArrayBuffer, isolation headers, database copies, schema changes, or
page-size changes are needed. SQL assets load once per provider worker.

VFS initialization opens the remote file without downloading it in full.
Indexed queries can fetch a small subset of its pages. Scan-heavy metadata and
market queries can require thousands of remote reads and take substantially
longer. The report-wide account-holder query remains a separate SQL performance
issue. Reloading discards the worker's cache and opens a fresh session.
